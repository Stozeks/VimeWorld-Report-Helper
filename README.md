# VimeWorld Report Helper

> Локальный инструмент поддержки модерации для VimeWorld Reports.

**VimeWorld Report Helper (VRH)** — браузерное расширение, которое дополняет интерфейс VimeWorld Reports и помогает модератору быстрее анализировать игровые сообщения, находить потенциальные нарушения и принимать решение по репорту.

VRH постепенно вырос из обычной боковой панели в полноценную систему анализа сообщений: нормализация текста, несколько уровней распознавания, контекстный анализ, Adaptive Recognition, локальное обучение, исключения, классификация нарушений и визуальные рекомендации работают как единый pipeline.

Главный принцип проекта остаётся неизменным:

> **VRH помогает модератору принять решение, но не принимает решение вместо него.**

Расширение не выдаёт наказания автоматически. Оно анализирует репорт, показывает найденные места, классифицирует возможные нарушения и оставляет окончательное решение человеку.

## Главная идея VRH

Сильно упрощённо обработка выглядит так:

```text
REPORT
   ↓
MESSAGE ANALYSIS
   ↓
NORMALIZATION
   ↓
OFFICIAL + BUILT-IN + LEARNED KNOWLEDGE
   ↓
CONTEXT & ADAPTIVE RECOGNITION
   ↓
VIOLATION CLASSIFICATION
   ↓
HIGHLIGHTING & REASON RECOMMENDATION
   ↓
MODERATOR DECISION
```

Сканирование не строится вокруг одного огромного списка запрещённых слов.

Вместо этого VRH объединяет несколько независимых источников информации и только после этого формирует итоговый результат.

---

# Сканер нарушений

Кнопка **«СКАНИРОВАТЬ РЕПОРТ»** запускает основной pipeline анализа сообщений.

Сканер получает сообщения игрока, нормализует текст и последовательно проверяет его через несколько уровней распознавания.

Он способен учитывать:

- официальную базу;
- встроенные recognition aliases;
- точные совпадения;
- искажённые формы;
- склеенные варианты;
- нестандартные символы;
- обученные модератором варианты;
- исключения;
- контекст между сообщениями;
- Adaptive Recognition;
- Relative Context / Relative Abuse.

Результаты разных механизмов объединяются перед отображением.

    width="100%"
  >
</p>

<p align="center">
  <sub>
    Найденные слова и фразы отмечаются непосредственно в истории сообщений,
    поэтому модератору не приходится отдельно искать источник срабатывания сканера.
  </sub>
</p>

VRH старается не просто сказать:

> «В репорте найдено нарушение».

Система показывает **где именно** она его увидела.

Для этого используется отдельный `Unified Highlighter`.

Он получает дескрипторы от разных систем анализа и отвечает за единую отрисовку подсветки. Благодаря этому несколько модулей не пытаются независимо изменять один и тот же DOM-фрагмент.

У дескрипторов существуют приоритеты, поэтому при пересечении разных типов распознавания VRH может выбрать более достоверный источник.

# Классификация нарушений

Одно из ключевых отличий текущей версии VRH — найденное совпадение больше не является просто «подозрительным словом».

Система пытается определить, **к какой категории относится обнаруженное нарушение**.

Например:

```text
Мат / Аморал
Оскорбление игроков
Оскорбление игроков + Мат
Оскорбление родственников
...
```

После классификации результат связывается с соответствующей причиной в панели.

  <img

  >
</p>

<p align="center">
  <sub>
    Вместе с найденной фразой VRH определяет категорию нарушения
    и визуально отмечает соответствующую плитку причины.
  </sub>
</p>

После сканирования VRH автоматически подсвечивает причины, соответствующие найденным нарушениям.

Разные категории имеют собственное визуальное состояние, поэтому результат анализа виден прямо в основной панели.

Это позволяет перейти от:

```text
нашли подозрительное слово
```

к:

```text
нашли совпадение
        ↓
поняли категорию
        ↓
связали с причиной
        ↓
показали рекомендацию
```

Подсветка плитки — **рекомендация**, а не автоматический выбор наказания.

---

# Несколько уровней знаний

VRH специально не смешивает все данные сканера в один словарь.

Система разделяет знания по происхождению.

```text
OFFICIAL KNOWLEDGE
        +
BUILT-IN RECOGNITION
        +
LEARNED KNOWLEDGE
        +
CONTEXT
        +
EXCEPTIONS
        ↓
FINAL RESULT
```

Такое разделение позволяет развивать распознавание, не изменяя официальные данные.

---

## Официальные данные

Официальные причины и базовые данные используются как стабильный слой.

VRH не должен самостоятельно придумывать, сокращать или изменять официальные формулировки причин наказаний.

Система обучения также **не изменяет официальный словарь**.

---

## Built-in Recognition Knowledge

В проекте существует отдельный слой встроенных recognition knowledge / aliases.

Он предназначен для известных форм, которые VRH должен понимать из коробки:

- устойчивые варианты написания;
- частые обходы;
- алиасы;
- известные искажения;
- дополнительные формы для классификации.

Это не Learning Store и не официальный словарь.

Так VRH может расширять собственное распознавание, сохраняя происхождение знания понятным.

---

# Adaptive Recognition

Игроки редко пишут проблемные слова в идеально словарной форме.

На практике встречаются:

- опечатки;
- замены букв цифрами;
- смешивание раскладок;
- лишние символы;
- намеренное коверкание;
- склеивание слов;
- похожие Unicode-символы;
- нестандартные формы сленга.

Поэтому поверх обычного поиска работает отдельный слой **Adaptive Recognition**.

В него входят:

- `Text Normalizer`;
- `Recognition Engine`;
- fuzzy matching;
- built-in aliases;
- обработка вариантов написания;
- Learning Store;
- система исключений;
- тестовая инфраструктура распознавания.

Adaptive Recognition работает как дополнительный уровень и не должен уничтожать результаты более точных механизмов.

# Локальное обучение сканера

<p align="center">
  <img
    src="docs/images/scanner-learning.png"
    alt="VimeWorld Report Helper — локальное обучение сканера"
    width="100%"
  >
</p>

<p align="center">
  <sub>
    Неизвестный вариант можно вручную подтвердить и сохранить:
    после обучения VRH способен распознавать его в следующих репортах.
  </sub>
</p>

Одна из основных особенностей VRH — возможность постепенно обучать сканер на реальных случаях.

Если система не знает определённое слово или намеренно искажённую форму, модератор может выделить её непосредственно в сообщении и использовать:

**🎓 Обучить сканер**

После этого выбирается категория нарушения.

Например:

```text
неизвестная форма
        ↓
ручное подтверждение
        ↓
категория нарушения
        ↓
Learning Store
        ↓
следующий репорт
        ↓
автоматическое обнаружение
```

При следующем появлении сохранённого варианта VRH уже может учитывать его во время сканирования.

### Важно

Обучение:

- не изменяет официальный словарь;
- хранится отдельно;
- остаётся локальным;
- связано с категорией нарушения;
- может использоваться системой подсветки;
- предназначено для подтверждённых модератором случаев.

Таким образом, сканер постепенно адаптируется к реальному игровому сленгу и новым способам обхода обычного поиска.

---

# Исключения и false positives

Обучение работает в обе стороны.

Если сканер считает обычное слово нарушением, его можно занести в исключения.

Итоговая логика выглядит примерно так:

```text
potential match
      ↓
knowledge source
      ↓
recognition
      ↓
exception check
      ↓
accepted / rejected
```

Это позволяет постепенно уменьшать количество false positives без удаления полезных правил из основной базы.

---

# Контекст между сообщениями

Не каждое нарушение можно определить по одному сообщению.

Иногда смысл появляется только при чтении нескольких соседних сообщений.

VRH имеет отдельные системы для таких случаев:

- `Relative Context`;
- `Relative Abuse`;
- cross-message knowledge.

Они могут учитывать:

- соседние сообщения;
- разделённые фразы;
- обращения;
- упоминания родственников;
- относительные оскорбления;
- ситуации, когда важные части выражения находятся в разных сообщениях.

Например:

```text
MESSAGE #1 ─┐
            ├─→ CONTEXT ANALYSIS → possible violation
MESSAGE #2 ─┘
```

Это позволяет не пытаться свести весь анализ исключительно к отдельным токенам.

---

# Unified Highlighter

По мере роста проекта несколько разных систем начали находить собственные совпадения:

```text
Official Scanner ──────┐
Built-in Knowledge ────┤
Learning Store ────────┤
Adaptive Recognition ──┼─→ Unified Highlighter → DOM
Relative Context ──────┤
Relative Abuse ────────┘
```

Чтобы каждый модуль не редактировал сообщения самостоятельно, подсветка централизована.

`Unified Highlighter` принимает результаты разных источников, учитывает диапазоны и приоритеты и затем выполняет единый проход по интерфейсу.

Это один из важных архитектурных слоёв текущей версии VRH.

---

# Reason Recommendation

Результат сканирования используется не только для подсветки текста.

После классификации VRH формирует рекомендации для панели причин.

Например:

```text
detected text
      ↓
INSULT
      ↓
player-insult
      ↓
«Оскорбление игроков»
      ↓
recommended tile
```

Если обнаружено комбинированное нарушение, система может рекомендовать более точную составную категорию вместо нескольких менее подходящих отдельных вариантов.

Рекомендация не нажимает плитку автоматически и не выдаёт наказание.

# Flood Scanner

Flood Scanner работает независимо от основного Violation Scanner.

Он предназначен для анализа признаков флуда, включая:

- повторяющиеся сообщения;
- обычный flood;
- flood символами;
- связанные паттерны повторения.

Результат отображается отдельно, чтобы логика флуда не смешивалась с классификацией остальных нарушений.

---

# Информация об игроках

VRH содержит отдельный слой **Player Identity** для работы с информацией об игроке непосредственно в интерфейсе репорта.

Он отвечает за получение, кэширование и отображение доступных данных, включая:

- игровую голову;
- никнейм;
- ранг;
- визуальное оформление ранга;
- дополнительную информацию, доступную интерфейсу.

Логика Player Identity отделена от Violation Scanner: получение информации об игроке не должно зависеть от механизма поиска нарушений.

### Почему в публичной документации скрываются Player Identity данные

Часть этой системы работает с информацией, отображаемой на внутренней странице VimeWorld Reports.

Поэтому реальные игровые головы, ники, идентификаторы репортов и связанные с ними данные намеренно скрываются на публичных демонстрационных скриншотах.

# Локальная статистика

VRH ведёт локальную статистику работы модератора.

Сейчас система может отображать:

- количество закрытых репортов;
- количество отклонённых;
- общее количество обработанных;
- заработанные баллы;
- прогресс за текущий месяц.

Статистика существует как вспомогательный локальный инструмент и не требует отдельного сервера.

# Текстовые инструменты

В интерфейсе присутствуют небольшие инструменты для работы с сообщениями.

В частности, можно преобразовывать текст между раскладками:

```text
ENG → RUS
RUS → ENG
```

Это полезно, когда русская фраза была набрана в английской раскладке или наоборот.

# Scanner Benchmark

Чем сложнее становится распознавание, тем опаснее исправлять один случай и случайно ломать несколько уже работающих.

Поэтому в проекте используется отдельный подход к regression-проверке сканера.

Тестовые случаи можно разделять на:

```text
SHOULD MATCH
SHOULD NOT MATCH
```

Первый набор проверяет, что известные нарушения продолжают находиться.

Второй — что обычные слова не начинают ошибочно определяться как нарушения.

Scanner Benchmark нужен для развития Adaptive Recognition и контроля false positives / missed detections.

```text

                                 ▼
                       ┌───────────────────┐

                       └─────────┬─────────┘

              │                  │                  │
              ▼                  ▼                  ▼
        OFFICIAL DATA       BUILT-IN DATA      LEARNED DATA

                       ADAPTIVE RECOGNITION
```

По мере роста проекта тяжёлые участки продолжают выноситься в отдельные модули.

# Локальные данные

Текущая версия VRH не требует собственного backend для основной работы.

Локально могут храниться:

- настройки;
- статистика;
- learned aliases;
- learned rules;
- исключения;
- другие накопленные данные сканера.

Для локального хранения используется браузерное storage, включая `chrome.storage.local`.

Это позволяет системе обучения работать без изменения официальных файлов и без обязательной передачи накопленных данных на внешний сервер.

# Принципы проекта

VRH развивается вокруг нескольких правил.

### 1. Moderator-in-the-loop

Сканер помогает человеку, а не заменяет его.

### 2. Официальные данные отдельно

Экспериментальное распознавание не должно незаметно изменять официальные причины или словари.

### 3. Обучение отдельно

Новые варианты хранятся как отдельный слой знаний.

### 4. False positives имеют значение

Система должна уметь не только узнавать новое нарушение, но и понимать, что определённый случай нарушением **не является**.

### 5. Контекст важнее одного слова

Совпадение токена не всегда достаточно для корректной классификации.

### 6. Объяснимый результат

По возможности модератор должен видеть не только рекомендацию, но и конкретное место, из-за которого она появилась.

---

# Что проект не делает

VRH **не является системой автоматической модерации**.

Он не должен:

- самостоятельно выдавать муты;
- автоматически считать игрока виновным;
- заменять решение модератора;
- изменять официальную причину наказания;
- считать любое fuzzy-совпадение доказанным нарушением.

Сканер может ошибаться.

Именно поэтому интерфейс построен вокруг подсветки, рекомендаций и подтверждения человеком.

# Текущее состояние

Проект находится в активной разработке.

Основной рабочий цикл уже сформирован:

```text
открыть репорт
      ↓
просмотреть сообщения
      ↓
запустить анализ
      ↓
увидеть найденные фрагменты
      ↓
получить рекомендации причин
      ↓
проверить результат
      ↓
принять решение
```

При этом архитектура продолжает развиваться по мере появления реальных кейсов.

# Дальнейшее развитие

В следующих версиях рассматриваются дальнейшие улучшения архитектуры и инструментов анализа, в частности:

Конкретные функции добавляются после проверки предыдущих изменений на реальных репортах.
